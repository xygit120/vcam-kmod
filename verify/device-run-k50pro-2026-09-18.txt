[4] what this run establishes

  * A real dma-buf from /dev/dma_heap/system is pinned by REGISTER_BUF, i.e.
    dma_buf_get() on this device's kernel accepted the producer's fd. The
    memfd fallback could not have proved this: dma_buf_get() rejects a memfd.
  * The pose rules recovered from FUN_005415b4 are correct on real hardware:
    autopose 90 -> 180 deg with mirror forced on, and an explicit 45 deg folds
    to 0 with the mirror flag taken from VCAM_F_MIRROR.
  * The tearing guard holds: SUBMIT into a HELD slot and UNREGISTER of a HELD
    slot are both refused with EBUSY, so a producer cannot overwrite a buffer
    the consumer is still reading.
  * The range/loop decision drops a frame past range_end when looping is off
    and does not queue it.
  * Every counter in vcam_stats matches the sequence of operations, so the
    state machine has no hidden transitions.


[5] findings that only a real load could produce

  a) __versions is EMPTY in the built .ko, and the device loads it anyway.
     CONFIG_MODVERSIONS=y makes the loader compare a CRC only for the symbols
     the module actually lists in __versions. An empty section means "version-
     check nothing", which is weaker than intended but accepted. The CI check
     therefore reports "0 CRC(s) match the device, 0 mismatch" -- that is a
     property of the artifact, not a failure of the build, and the merged
     14655-entry Module.symvers in device/ is what the module was built against.

  b) Symbols that were not in the mined 15-symbol device profile resolved on the
     device without complaint: param_ops_uint (from module_param),
     arm64_const_caps_ready, cpu_hwcap_keys, cpu_hwcaps and
     gic_nonsecure_priorities (from inlined arch code). They come from the DDK
     tree's own Module.symvers, and the device exports all of them.

  c) /dev/vcam is 0600 root:root and labelled u:object_r:device:s0; the KernelSU
     su domain (u:r:ksu:s0) is allowed to open it while SELinux is enforcing, so
     no policy change was needed to run the test. A non-root consumer (an app, or
     cameraserver itself) would still need a policy entry for the node -- that is
     the deployment step this run does not cover.

  d) rmmod followed by insmod works repeatedly, so the pool releases every
     dma-buf reference it took; a leaked reference would keep the buffer alive
     and eventually fail the second registration.


[6] host-side gotcha worth recording

    KernelSU's su treats a compound command as root only when the device shell
    sees it quoted as ONE word. Over `adb shell` from Windows:

      adb shell 'su -c "id; id"'     -> first id is root, the rest runs as the
                                        unprivileged adb shell (uid 2000)
      adb shell "su -c 'id; id'"     -> the whole compound runs as root

    Under the first form `open("/dev/vcam")` fails with EACCES from the uid-2000
    shell, which looks exactly like a SELinux denial and is not one. The AVC
    log is the discriminator: no chr_file denial is recorded for that open.
